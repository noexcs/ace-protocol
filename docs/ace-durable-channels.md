# 持久型通道（durable channels）—— 语义补遗

状态：**已确认的语义，尚未实现。** 本文只定语义与边界，不改代码、不改 README、不动配置 schema。

词汇：本文一律说 **Server**，指会话所连接的那台 Redis；不使用 "broker"。

## 1. 两个层次：持久型通道，与它的用法

**持久型通道（durable channel）**是一类**不属于任何活会话的地址** —— 它不是某个会话的收件箱，而是由配置声明出来、
比任何一个会话都活得久的通道。它带来三件事：

- **声明即存在**：唯一的来源是配置文件；Redis 侧首次触达时隐式创建（§4）；
- **组不随会话结束销毁**：会话下次回来，接着上次的位置读（§5）；
- **TTL 窗口即追补窗口**：窗口内能补上，窗口外即丢（§5）。

**主题（topic）只是它的第一种用法**：一块被订阅的**公告板** —— 多个会话订阅同一个通道，每个订阅者各得一份（扇出）。

同一个底座上将来还可能长出别的用法，例如：

- **单订阅者的信箱**：一个长期地址，对端在它离线时也能投（TTL 窗口内）。这本质上就是"只有一个订阅者的持久型通道"，
  **不需要新机制**，也不需要新语义；
- **抢单队列**：多个消费者共享一个组、竞争消费。**本版明确不做** —— 它与 §5 的"每个订阅者各得一份"正好相反。

**本版只实现 topic 这一种用法**；其余用法在出现之前不做设计。

## 2. 地址

```text
<ns>:<username>:topic:<name>          # 例：ace:alice:topic:broadcast
```

- 第三段是**用法（种类）段**，**今天唯一的值是 `topic`，且为保留段**：任何 agent 名都不得为 `topic`。
  会话通道是 `<ns>:<username>:<agent>:<sessionId>`，第三段是 agent 名，两类地址因此不可能相撞。
- **为什么不现在就把"种类"做成多成员枚举**：`docs/ace-plan.md` §1.2 已经为同类问题定过调子 ——
  只有一个成员的枚举属于**投机抽象**，等第二个真实成员出现再做。地址已经预留了这一段，所以将来加第二种用法
  **不需要改地址格式**，只要给它一个新的字面量。
- 配置里写**裸名**（`broadcast`）= 自己命名空间下的通道；写**四段全名** = 别人的通道。

## 3. 配置

位置不变：`servers.<serverName>.subscribe`。每个条目**两项**：

```json
"subscribe": [
  { "channel": "broadcast", "activation": "next_turn" },
  { "channel": "ace:bob:topic:deploy", "activation": "manual" }
]
```

- 裸字符串（`"broadcast"`）是简写，`activation` 取 `defaultActivation`；现有的纯字符串配置继续有效。
- **没有** `ttl`、没有 `accept`、没有别的键。TTL 见 §5，发布权限见 §7。
- 订阅权限：**无** —— 任何人都可以订阅任何持久型通道。

## 4. 存在方式：没有创建，也没有发现

- 持久型通道**没有创建动作、没有注册表、没有列表工具**：**配置文件是它存在的唯一来源**（用户手写）。
- Redis 侧**首次触达时隐式创建**：发布方 `XADD`（键不存在即建立）；订阅方
  `XGROUP CREATE <stream> <group> $ MKSTREAM`。
- 因此**不提供** `ace_channels` 之外的发现能力，也**不列主题**；`ace_agents` 只列活会话，永远不列持久型通道。

## 5. 投递、组与 TTL

先写"持久"带来的性质（对所有用法成立）：

- **每个订阅会话一个 consumer group**，组名 = **该会话自己的通道**（`<ns>:<username>:<agent>:<sessionId>`）。
- **组不随会话结束销毁**：会话下次回来，从上次位置继续读。
- **TTL = 全局常量 24 小时**（不写进配置），它就是**追补窗口**：
  - 窗口内：会话不在线期间发布、且尚未过期的消息，回来时能读到 —— 这由 Redis Streams 的组语义天然提供，
    **不需要 offset，也不需要回放机制**；
  - 窗口外：消息已过期即丢，**不承诺追补**。
- **清理是惰性的、谁触达谁做**（幂等，不需要独立的 janitor 服务）：
  - `XTRIM <stream> MINID ~ <now - ttl_ms>-0` 裁掉过期条目；
  - 同时把"**已被裁剪、但仍挂在某个 PEL 里**"的条目 `XACK` 掉 —— 否则 `XPENDING` 会留下永远无法认领的幽灵条目，
    `XAUTOCLAIM` 也捞不回来。

topic 这一用法在投递上的含义只有一条：**因为组名按会话区分，同一通道对不同订阅者就是扇出，互不抢消息**。

## 6. activation：订阅方优先

- 订阅里写的 `activation` 就是该通道对该会话的**生效值** —— 由**接收方**决定自己"被怎么打断"。
- 发送方信封里的 `activation` **只对点对点发到会话通道的事件生效**；发到持久型通道时以订阅方的声明为准。
- `manual` 的含义：**宿主挂起** → 展示给用户 → **用户批准** → **宿主激活**。直接复用现有的
  `ace_pending` / `ace_activate`；唯一的扩展点是 pending 列表里要带上**来源通道**。

## 7. 权限：本版不做发布限制

- ACE 0.1 无鉴权，Server 是交汇点、不是安全边界 —— 这一条对整个协议成立，持久型通道不例外。
- **本版不实现"发布权限"**，原因：没有创建入口、没有注册表，权限无处声明；且当前没有真实的外部生产者。
- 现在生效的兜底：**未被告知过的发送方，宿主会问它的用户**（宿主策略，与通道配置无关）。
- 将来真要做时的两条路（届时再定）：
  - **宿主级**：每个宿主一份"我接受哪些发送方"的名单（不区分通道）—— 协作型强制，挡误发不挡恶意方；
  - **Server 级**：给身份配 Redis ACL（只允许 `+xadd` 到特定键模式）—— 真正的边界，代价是把 Redis 认证变成信任根。

## 8. 明确不做

创建入口 · 发现/列表（含主题列表） · 订阅权限 · 服务端 ACL · **抢单（共享组）队列** ·
单订阅者信箱的专门语义（它是同一底座的另一种用法，不需要新机制） · 超出 TTL 的投递保证 · 通道级的 per-channel 配置项。

## 9. 与现状的关系

| | Pi / oh-my-pi（`ace-omp`） | DeepSeek Harness（`ace-dsh`） |
|---|---|---|
| 读持久型通道 | 已支持（`subscribe`） | **只读 live 通道**，`subscribe` 被报告但忽略 |
| 条目形状 | 纯字符串数组 | 同上（本补遗要扩展为对象形式） |

两边都要对齐到本文语义：对象形式的条目、组名 = 会话自身的通道、**全局 24h TTL**、**订阅方优先的 activation**。
Pi 侧现有的组名、TTL 与 activation 优先级**需要先核对再改** —— 本文不假设它已经一致。

## 10. 尚未定的（记在这里，免得以后被当成 bug）

- **组与 PEL 的长期回收**：组不销毁 + 会话永久消失 → 死组会持续积累。是否要"超过 N 倍 TTL 未读即回收"的策略。
- **TTL 的 per-channel 覆盖**：现在刻意不做；将来是否需要一个总开关式的覆盖。
- **schema 向后兼容**：对象形式与既有纯字符串配置共存的联合类型。
- **第二种用法出现时**：第三段是给它一个新的字面量（不动地址格式），还是届时要重新考虑分段 —— 到时再定。
