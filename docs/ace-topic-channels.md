# 持久型（主题）通道 —— 语义补遗

状态：**已确认的语义，尚未实现。** 本文只定语义与边界，不改代码、不改 README、不动配置 schema（schema 的扩展见 §3、§10）。

词汇：本文一律说 **Server**，指会话所连接的那台 Redis；不使用 "broker"。

## 1. 是什么，不是什么

主题通道是一个**不属于任何活会话的地址** —— 它不是某个会话的收件箱，而是一块被订阅的公告板。

- **是**：扇出（每个订阅者各得一份）、配置声明即存在、TTL 窗口内可追补；
- **不是**：不承诺超出 TTL 的投递；不是任务队列（没有抢单语义）；不是服务发现（没有主题列表）。

当下它的使用者是**你自己的若干会话**（例如一条广播让所有会话都知道）。面向外部生产者（CI、告警、服务）的用法留在以后 ——
到那时才需要讨论发布权限怎么强制（§7）。

## 2. 地址

```text
<ns>:<username>:topic:<name>          # 例：ace:alice:topic:broadcast
```

- 第三段固定为字面量 `topic`，且是**保留段**：任何 agent 名都不得为 `topic`。会话通道是
  `<ns>:<username>:<agent>:<sessionId>`，第三段是 agent 名，两类地址因此不可能相撞。
- 配置里写**裸名**（`broadcast`）= 自己命名空间下的主题；写**四段全名** = 订阅别人的主题。

## 3. 配置

位置不变：`servers.<serverName>.subscribe`。每个条目**两项**：

```json
"subscribe": [
  { "channel": "broadcast", "activation": "next_turn" },
  { "channel": "ace:bob:topic:deploy", "activation": "manual" }
]
```

- 裸字符串（`"broadcast"`）是简写，`activation` 取 `defaultActivation`；现有的纯字符串配置继续有效。
- **没有** `ttl`、没有 `accept`、没有别的键。TTL 见 §5，发布权限见 §7。
- 订阅权限：**无** —— 任何人都可以订阅任何主题。

## 4. 存在方式：没有创建，也没有发现

- 主题**没有创建动作、没有注册表、没有列表工具**：**配置文件是它存在的唯一来源**（用户手写）。
- Redis 侧**首次触达时隐式创建**：发布方 `XADD`（键不存在即建立）；订阅方
  `XGROUP CREATE <stream> <group> $ MKSTREAM`。
- 因此**不提供** `ace_topics` 之类的发现工具；`ace_agents` 只列活会话，**永远不列主题**。

## 5. 投递与生命周期

- **每个订阅会话一个 consumer group**，组名 = **该会话自己的通道**（`<ns>:<username>:<agent>:<sessionId>`）。
  于是同一主题对不同订阅者就是扇出，互不抢消息。
- **组不随会话结束销毁**：会话下次回来，从上次位置继续读。
- **TTL = 全局常量 24 小时**（不写进配置），它就是**追补窗口**：
  - 窗口内：会话不在线期间发布、且尚未过期的消息，回来时能读到 —— 这由 Redis Streams 的组语义天然提供，
    **不需要 offset，也不需要回放机制**；
  - 窗口外：消息已过期即丢，**不承诺追补**。
- **清理是惰性的、谁触达谁做**（幂等，不需要独立的 janitor 服务）：
  - `XTRIM <stream> MINID ~ <now - ttl_ms>-0` 裁掉过期条目；
  - 同时把"**已被裁剪、但仍挂在某个 PEL 里**"的条目 `XACK` 掉 —— 否则 `XPENDING` 会留下永远无法认领的幽灵条目，
    `XAUTOCLAIM` 也捞不回来。

## 6. activation：订阅方优先

- 订阅里写的 `activation` 就是该主题对该会话的**生效值** —— 由**接收方**决定自己"被怎么打断"。
- 发送方信封里的 `activation` **只对点对点发到会话通道的事件生效**；发到主题时以订阅方的声明为准。
- `manual` 的含义：**宿主挂起** → 展示给用户 → **用户批准** → **宿主激活**。直接复用现有的
  `ace_pending` / `ace_activate`；唯一的扩展点是 pending 列表里要带上**来源主题**。

## 7. 权限：本版不做发布限制

- ACE 0.1 无鉴权，Server 是交汇点、不是安全边界 —— 这一条对整个协议成立，主题不例外。
- **本版不实现"主题的发布权限"**，原因：没有创建入口、没有注册表，权限无处声明；且当前没有真实的外部生产者。
- 现在生效的兜底：**未被告知过的发送方，宿主会问它的用户**（宿主策略，与主题配置无关）。
- 将来真要做时的两条路（届时再定）：
  - **宿主级**：每个宿主一份"我接受哪些发送方"的名单（不区分主题）—— 协作型强制，挡误发不挡恶意方；
  - **Server 级**：给身份配 Redis ACL（只允许 `+xadd` 到特定键模式）—— 真正的边界，代价是把 Redis 认证变成信任根。

## 8. 明确不做

创建入口 · 主题发现/列表 · 订阅权限 · 服务端 ACL · 抢单（共享 group）语义 · 超出 TTL 的投递保证 ·
主题级的 per-channel 配置项。

## 9. 与现状的关系

| | Pi / oh-my-pi（`ace-omp`） | DeepSeek Harness（`ace-dsh`） |
|---|---|---|
| 读持久通道 | 已支持（`subscribe`） | **只读 live 通道**，`subscribe` 被报告但忽略 |
| 条目形状 | 纯字符串数组 | 同上（本补遗要扩展为对象形式） |

两边都要对齐到本文语义：对象形式的条目、组名 = 会话自身的通道、**全局 24h TTL**、**订阅方优先的 activation**。
Pi 侧现有的组名、TTL 与 activation 优先级**需要先核对再改** —— 本文不假设它已经一致。

## 10. 尚未定的（记在这里，免得以后被当成 bug）

- **组与 PEL 的长期回收**：组不销毁 + 会话永久消失 → 死组会持续积累。是否要"超过 N 倍 TTL 未读即回收"的策略。
- **TTL 的 per-channel 覆盖**：现在刻意不做；将来是否需要一个总开关式的覆盖。
- **schema 向后兼容**：对象形式与既有纯字符串配置的共存策略（`subscribe` 条目的联合类型）。
